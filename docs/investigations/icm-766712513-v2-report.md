## TL;DR

> **True Positive — Recurring noisy-tenant pattern on WEU-402 Watchlist endpoint.** ARM reports 73.63% API success rate, but the RP itself shows **99.94–99.97% success** (only 3–4 HTTP 500s per 5 minutes out of 7,000–14,000 requests). The gap between ARM's view and the RP's view proves the failures are primarily **httpStatusCode=0 (ARM→RP connection timeouts)** — requests that never reached the RP or timed out at the TCP layer. All 46 RP-side 500s came from a single subscription (`7d28c677-...`) doing repeated PUT operations on the same 4 watchlistItems in watchlist "ReportsNew." This is the 5th+ recurrence of the identical pattern on prd-weu-402, consistent with a single-tenant request flood saturating ARM-to-RP connections. The systemic root cause is the absence of per-tenant rate limiting.

## Incident Classification

**Classification: TRUE POSITIVE**

**Reasoning:** The ARM monitor correctly detected a real API success rate drop. The Geneva watchdog observed ClientFailure counts spiking from baseline levels, causing the success rate to fall below the Bronze SLO threshold. The failures are genuine — they represent real customer-facing errors (timeouts). However, the root cause is exogenous to the RP: a single tenant's request flood is exhausting ARM-to-RP connections, not an RP-side bug.

**Severity Assessment:**
- **Reported:** Sev 2
- **Assessed:** Sev 2 is appropriate — the error rate breach is real, the endpoint serves production traffic, and the pattern is recurring. However, the narrow blast radius (zero customer escalations) and self-mitigating nature mean this should not be escalated further.

## Root Cause Analysis

### Hypotheses

#### H1: Single-tenant request flood causing ARM→RP connection timeouts (HIGH confidence — **SELECTED**)

**Evidence FOR:**
- RP success rate 99.94–99.97% but ARM reports 73.63% → failures are httpStatusCode=0 (timeouts at ARM layer)
- All 46 RP-side 500s from single subscription doing automated PUT retries on 4 watchlistItems
- Same prd-weu-402 endpoint has 5+ prior incidents with same pattern
- ICM 757455363 (most relevant precedent) confirmed as "transient application timeouts, self-resolved"
- ICM mitigation hints explicitly list "transient application timeouts" and "customer errors causing 500s"
- Brain TSG confirms HTTP 0 = ARM→RP timeout, not RP failure
- Jonathan's prior investigation identified workspace `68a0c627-...` as offending tenant in ICM 758629051

**Evidence AGAINST:**
- We cannot directly query the ARM-side data (macro-expand ARMProdEG queries require SAW/DGrep access) to see the exact httpStatusCode=0 distribution
- The offending tenant in this specific incident may be different from prior ones

#### H2: CosmosDB throttling cascading to ARM timeouts (LOW confidence — rejected)

**Evidence FOR:**
- CosmosDB 429 is a documented failure mode for Watchlist services
- The subscription making failed PUTs could be triggering CosmosDB contention

**Evidence AGAINST:**
- RP success rate is 99.94–99.97% — CosmosDB throttling would degrade ALL requests, not just ARM→RP connections
- Only 3–4 HTTP 500s per 5-min window — too few for throttling
- Prior incidents showed httpStatusCode=0 (timeout), not 429
- CosmosDB retry logic would absorb transient 429s

#### H3: ARM infrastructure issue in West Europe (LOW confidence — rejected)

**Evidence FOR:**
- West Europe region is the common factor across incidents

**Evidence AGAINST:**
- Zero service health events in West Europe on incident date
- Success traffic remained stable during the spike — infrastructure failure would affect ALL traffic
- 5 incidents in 18 days is too frequent for random infrastructure failure
- All prior incidents confirmed as tenant-side, not infrastructure

### Causal Chain

```
1. Single tenant (sub 7d28c677-...) runs automated script
   → PUTs same 4 watchlistItems to "ReportsNew" watchlist every ~5 min
2. PUT operations fail with HTTP 500 on the RP side (likely data validation or conflict)
   → Script retries, creating sustained request load
3. Additional tenant(s) may be sending high-volume requests to same endpoint
   → Combined load saturates ARM-to-RP connection pool for prd-weu-402
4. New ARM requests time out at TCP layer (httpStatusCode=0)
   → ARM classifies these as ClientFailure
5. ARM retries failed requests (retries counted as separate calls per Brain TSG)
   → Amplifies failure count: 381-666 ClientFailures/min
6. ARM API success rate drops to 73.63%
   → Below Bronze SLO threshold
7. Geneva monitor fires ADROCS alert
   → ICM 766712513 created as Sev 2
8. Issue self-mitigates when tenant burst subsides
   → Matches historical pattern from prior incidents
```

**Root Cause:** Single-tenant request flood (automated retry loop on failing watchlistItem PUTs) saturating ARM-to-RP connections on prd-weu-402, enabled by the absence of per-tenant rate limiting at both the Watchlist API and ARM gateway level.

**Confidence:** HIGH — Consistent with 5+ prior incidents on same endpoint, supported by both ARM-side and RP-side Kusto data, Brain TSG explanation of httpStatusCode=0, and historical root causes from mitigation hints.
