## Executive Summary

The CosmosDbPublisher service in North Europe experienced a severe Cosmos DB Request Unit (RU) throttling event, causing a cascade where retry storms built up an EventHub consumer backlog. The pipeline latency monitor fired 49 times over roughly 3.5 hours. No customers were impacted. The root cause is a spike in Cosmos DB write volume that exhausted provisioned RU capacity — a recurrent pattern seen in 30 similar incidents across westeurope, eastus, and northeurope since February 2025. All prior incidents resolved autonomously (median time ~3–4 hours) without intervention.

**Classification: True Positive — Recurring Operational Pattern**  
**Customer Impact: None**  
**Severity Assessment: Correctly filed at Sev 2; actual end-user exposure is Sev 3/4 equivalent**

## Stage 3: Root Cause Analysis

### Hypotheses

**H1: Cosmos DB RU exhaustion triggered by a burst of indicator write operations** *(Primary)*

A spike in indicator write volume caused CosmosDbPublisher to exhaust the provisioned Cosmos DB throughput (RU/s). Cosmos DB responded with HTTP 429 (`TooManyRequests`) / sub-status 3200 (`RUBudgetExceeded`). CosmosDbPublisher entered a retry loop. Retrying writes slowed the EventHub consumer offset, building backlog. The TIPipeline latency monitor detected the lag and fired a Sev 2 alert.

Evidence:
- IcM Copilot annotation explicitly states `429/3200-RUBudgetExceeded`
- CosmosRUUsage rose to 4× baseline during the incident window (Geneva metrics)
- CosmosOperation count dropped 28% at 10:00 (reduced throughput during throttling)
- Identical pattern seen in 30 prior incidents, most recent just 9 days earlier (westeurope)
- westeurope keywords identify "legacy indicator upserts" as the trigger

**Confidence: HIGH**

---

**H2: NormalizationService burst feeding excess messages to EventHub** *(Secondary / Contributing)*

A burst upstream from NormalizationService could have flooded the EventHub with more messages than CosmosDbPublisher could process at its current RU capacity, rather than CosmosDbPublisher generating the RU spike itself.

Evidence for: NormalizationService is the highest-volume component by error count in the Kusto research (1.9M errors/hr baseline). A burst there could amplify downstream load.

Evidence against: The RU spike profile (gradual onset at 10:00, peak at 12:00, decline at 13:00) is more consistent with a large batch job than a sudden upstream burst. The westeurope incident explicitly named "legacy indicator upserts" as the cause — a batch-side trigger, not a streaming upstream trigger.

**Confidence: MEDIUM as a contributing factor; LOW as the sole cause**

---

**H3: Cosmos DB partition hotspot** *(Tertiary)*

Uneven key distribution could cause RU exhaustion on a single physical partition while overall RU headroom remains. This would produce 429s without a global RU spike.

Evidence against: The CosmosRUUsage metric shows a global 4× spike — not a localized partition issue. Global throttling points to aggregate RU capacity being exceeded, not a partition-level distribution problem.

**Confidence: LOW**

---

### Root Cause (Final)

**A high-volume batch of Cosmos DB write operations — most likely legacy indicator upserts from a scheduled or triggered batch job — caused aggregate RU consumption in the northeurope TI Cosmos DB account to spike to 4× its morning baseline. When consumption exceeded provisioned throughput, Cosmos DB throttled CosmosDbPublisher with HTTP 429 responses. CosmosDbPublisher's retry behaviour caused EventHub consumer lag to accumulate. The TIPipeline Latency Monitor detected this lag and fired a Sev 2 alert. No data was permanently lost; the retries ensure eventual consistency.**

### Causal Chain

```
Large batch of indicator upsert writes arrives
       ↓
CosmosDbPublisher submits writes to Cosmos DB (northeurope)
       ↓
Cosmos DB provisioned RU/s capacity exceeded (429 / 3200-RUBudgetExceeded)
       ↓
CosmosDbPublisher backs off and retries throttled writes
       ↓
Write throughput drops; EventHub consumer offset falls behind
       ↓
EventHub message backlog grows (pipeline "falling behind")
       ↓
TIPipeline Latency Monitor fires → IcM Sev 2 created (10:10 UTC)
       ↓
CosmosDbPublisher continues retries; Cosmos DB throttling gradually eases
       ↓
Watchdog eventually reports healthy → auto-mitigation (expected ~13:30–14:00 UTC)
```

**Overall Confidence: HIGH** — supported by direct metric evidence, IcM enrichment annotation, and 30 identical historical precedents.

## Stage 4: Remediation

### Immediate Actions (In-flight)

1. **No immediate intervention required.** Based on all 30 historical analogues, this incident self-resolves when the batch completes and Cosmos DB throttling eases. The health manager auto-mitigates once watchdogs report healthy for ~12 consecutive minutes.
2. **Monitor the ACTIVE state.** If the incident persists beyond 14:30 UTC (4+ hours from creation), manually escalate: check whether a long-running batch is still saturating RUs, and consider temporarily increasing Cosmos DB provisioned throughput (autoscale max) for the northeurope account.
3. **Acknowledge the incident** and set `howFixed: Transient` if self-resolved — matching the westeurope precedent.

### Short-Term Fixes (Within 1–2 Sprints)

1. **Implement batch write rate limiting in CosmosDbPublisher.** The publisher should detect 429 responses and apply adaptive throttling (exponential backoff with jitter and a maximum retry rate), rather than retrying immediately. This would reduce the retry storm that builds EventHub backlog.

2. **Separate provisioned throughput for legacy upsert batches.** If the root trigger is legacy indicator upsert jobs, these should either:
   - Run against a dedicated Cosmos DB container with its own RU budget, or
   - Be rate-limited at the job level to not exceed a fraction of the shared RU provisioning.

3. **Add a northeurope-specific TSG step** to the TIPipeline Latency Monitor TSG. Current TSG was written for westeurope context. The northeurope cluster has different Kusto access patterns.

### Long-Term Prevention

1. **Autoscale Cosmos DB throughput.** Enabling Cosmos DB autoscale with a higher max RU ceiling would allow the account to absorb write bursts without throttling. The 4× spike observed suggests the current provisioned capacity is too close to the steady-state write load.

2. **Eliminate the recurring pattern.** The 30 incidents over 13 months show this is a systemic design issue, not a one-off. The pipeline architecture needs demand-smoothing: either:
   - Back-pressure propagation from CosmosDbPublisher upstream to ingestion/normalization, or
   - Write buffering with a separate high-watermark queue so bursts absorb at the buffer layer, not the Cosmos DB layer.

3. **Downgrade monitor to Sev 3 with suppression.** Given the pattern is always transient and never customer-impacting, filing this at Sev 2 every time creates unnecessary oncall burden. Either:
   - Change monitor severity to Sev 3 for the first 2 hours, escalating to Sev 2 only if it persists, or
   - Add a 30-minute suppression window before firing.

4. **Track this pattern as a formal engineering work item.** The 30 incidents represent significant oncall toil. Assign an item to either fix autoscale or rate-limit the legacy batch job.
