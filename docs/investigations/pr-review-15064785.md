## Summary

This PR introduces a comprehensive TiExpert agent definition and supporting infrastructure for Threat Intelligence (STIX) operations within the Sentinel-TiPipeline repository. It adds 15 new files across three categories: an agent definition (`.github/agents/`), six skill documentation files (`.github/skills/`), and eight PowerShell validation scripts (`.github/scripts/`). The intent is to provide automated validation flows and documented API operation skills for STIX API, Bulk Actions, File Import, Ingestion API, LA Query, and StixWebApi.

**Review outcome:** While the scope and approach are sound, several security, reliability, and process concerns require resolution before merge. The PR has **zero human reviewers assigned**, which is itself a governance gap. Multiple issues related to error handling, potential secret exposure in examples, and documentation inconsistencies must be addressed.

## Finding Details

### Finding 1: Potential Secret Exposure in PPE Config
**File:** `.github/scripts/ti-config.ps1`  
**Severity:** High  
**Category:** Security  
**Confidence:** Medium (cannot read file contents)  
**Issue:** PPE configuration files commonly contain subscription IDs, workspace IDs, resource group names, and API endpoint URLs. If any secrets (API keys, connection strings, SAS tokens) are present in this file, they would be committed to the repository.  
**Suggestion:** Verify that `ti-config.ps1` contains only non-sensitive configuration (URLs, resource names). Any secrets must use Azure Key Vault references, environment variables, or `az account get-access-token` patterns. Consider adding a `.gitignore` entry for any local config overrides.

### Finding 2: Token Acquisition Patterns in Agent Definition
**File:** `.github/agents/tiexpert.agent.md`  
**Severity:** High  
**Category:** Security  
**Confidence:** High (confirmed via MerlinBot review)  
**Issue:** The agent definition includes inline PowerShell snippets demonstrating token acquisition via `az account get-access-token`. While the pattern itself is correct (using Azure CLI, not hardcoded tokens), the example code must be verified to contain no real token values, subscription IDs, or workspace IDs that could be exploited.  
**Suggestion:** Ensure all examples use placeholder values (e.g., `<your-subscription-id>`, `<your-workspace-id>`). Add a disclaimer that examples must be run with user's own credentials.

### Finding 3: No Human Reviewers Assigned
**File:** PR-level  
**Severity:** High  
**Category:** Process  
**Confidence:** High (confirmed via API — `reviewers: []`)  
**Issue:** The PR has zero human reviewers. Only MerlinBot (automated) has reviewed. For a PR that introduces an agent definition and PowerShell scripts that interact with Azure resources and APIs, human review is essential — especially for security review of token handling and API endpoint configuration.  
**Suggestion:** Assign at least one team member with security awareness as a required reviewer before merge.

### Finding 4: Silent Failure on Token Acquisition
**File:** `.github/agents/tiexpert.agent.md:39-40`  
**Severity:** Medium  
**Category:** Bug  
**Confidence:** High (confirmed via MerlinBot review)  
**Issue:** Token acquisition snippet uses `return` on failure. In a `.ps1` script context, `return` does not set a non-zero exit code, making failures invisible to automation and CI systems. Downstream API calls would fail with confusing auth errors instead of a clear "not logged in" message.  
**Suggestion:** Replace `return` with `exit 1` or `throw "FAIL: Run az login first."` to ensure proper failure signaling:
```powershell
$token = (az account get-access-token --resource $armBaseUrl --query accessToken -o tsv)
if (-not $token) { Write-Host "FAIL: Run az login first."; exit 1 }
```

### Finding 5: Polling Loop Ignores Failure State
**File:** `.github/skills/bulk-actions-api/SKILL.md`  
**Severity:** Medium  
**Category:** Bug  
**Confidence:** High (confirmed via MerlinBot review)  
**Issue:** The bulk actions polling loop only breaks on `Done` state. If the action transitions to `Failed`, the loop continues sleeping until `$maxRetries` is exhausted, wasting time and hiding the failure until timeout.  
**Suggestion:** Add a `Failed` state check:
```powershell
for ($i = 1; $i -le $maxRetries; $i++) {
    Start-Sleep -Seconds 5
    $resp = Invoke-RestMethod -Uri "..." -Method GET -Headers $headers
    if ($resp.properties.state -eq "Done") { break }
    if ($resp.properties.state -eq "Failed") { throw "Bulk action failed: $($resp.properties)" }
}
```

### Finding 6: Orchestrator Error Aggregation
**File:** `.github/scripts/validate-all.ps1`  
**Severity:** Medium  
**Category:** Design  
**Confidence:** Medium (cannot read file contents — inferred from file name and role)  
**Issue:** The `validate-all.ps1` orchestrator runs multiple validation scripts. Without proper error handling, a failure in one script may either halt all subsequent validations (fail-fast) or silently continue (fail-silent). Neither is ideal without explicit design choice.  
**Suggestion:** Implement one of:
- **Fail-fast with clear reporting:** Stop on first failure, report which script failed
- **Run-all with summary:** Collect exit codes from all scripts, report aggregate pass/fail at the end
- Ensure `$ErrorActionPreference = 'Stop'` or explicit try/catch patterns

### Finding 7: No CI Pipeline Integration
**File:** All validation scripts  
**Severity:** Medium  
**Category:** Testing  
**Confidence:** Medium (no pipeline YAML changes in this PR)  
**Issue:** The PR adds 6 validation scripts but no CI pipeline configuration to run them automatically. Without CI integration, these scripts are manual-only tools, reducing their value for regression detection and ongoing quality assurance.  
**Suggestion:** Add a pipeline YAML file (or extend an existing one) that runs `validate-all.ps1` on PR and/or scheduled triggers. This can be a follow-up PR if the team prefers to merge the scripts first.
